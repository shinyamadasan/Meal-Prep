Every discovery test passed because each injected its own tagged fixtures; the new specs assert against the shipped `sampleRecipes` instead. Fixed in four parts: (1) primary cooking-method chips never hide — an empty one is muted with an empty state naming the editor field that fills it; Rice cooker matches rice-cooker AND rice-cooker-steamer, Instant Pot matches instant-pot AND pressure-cooker (presentation grouping over existing `equipment[]`, no new field); Lowest effort aligned to the same `recipeEffortScore() <= 2` gate Home's "Easiest" uses and sorted by hands-on work, not clock. (2) 14 low-effort starter recipes (ids 27–40): 4 rice cooker, 4 oven, 3 Instant Pot, 3 no-cook, each written FOR its appliance and proven by a grep of its own instructions; the 26 originals byte-identical. (3) Opt-in delivery for existing installs — `ensureStarterRecipes()` stays first-run-only, a compact Cook prompt adds only genuinely absent recipes, presence is a permanent skip, and `AppState.deletions` is honoured so a deleted starter recipe is never resurrected (re-adding with a fresh `updatedAt` would have BEATEN its tombstone under LWW). (4) Seed object isolation — `[...sampleRecipes]` shared every recipe object with the module constant, and the exploit was reproduced end to end: the starter pack added a recipe pre-scaled to 8 servings and already favourited, carried over from an unrelated edit in the same session. Zero new persisted state. Reversible D-032 `done`. Recipes 26 → 40; live chips Rice cooker 4 / Oven 4 / Instant Pot 3 / No-cook 3. Production smoke 15/15. Known follow-ups recorded, not fixed: 180-day tombstone horizon, Firebase multi-device untested locally, `defaultStorageData`/`defaultCookingHacks` shallow-copy audit, Lowest effort deliberately broad at `<= 2` pending dogfooding.
