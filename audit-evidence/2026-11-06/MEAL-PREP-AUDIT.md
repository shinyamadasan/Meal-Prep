# Meal Prep product and technical audit — 2026-11-06

Meal Prep already contains the useful household loop. The highest return comes from making its stock claims, quantities, and recovery trustworthy. Adding another assistant or another planning surface would inherit the errors below.

## Sync and reliability risks — distinguish model evidence from live proof

- **Same-id cloud conflicts can discard newer values.** A direct call to `mergeCloudConflict` with remote quantity 5/newer timestamp and stale local quantity 6 returns 6; an empty local planned-batch list also replaces the remote plan. The transaction conflict union prefers local objects, while sign-in uses timestamp-aware `unionByIdLWW`. This is confirmed merge-function behavior. Frequency and full two-device timing were not measured against production. Simply switching to timestamps would still lose one of two concurrent portion decrements; that requires an explicit conflict policy.
- **A newer real-time snapshot replaces most mutable collections.** Pending local changes can be at risk. Immutable consumption facts receive stronger union handling. Offline reconnect, simultaneous devices, account-switch isolation, listener lifecycle, and actual backend rule enforcement need isolated emulator/two-context fault tests before claiming reliability.
- **Single-document growth and write amplification.** The main cloud payload includes append-only consumption facts/conflict evidence and the other collections. Autosave runs every 30 seconds without a dirty check. An open signed-in session can attempt approximately 120 root transactions/hour even if idle. Actual usage, cost, document headroom and household event volume were not measured. Photos are separated in cloud, which helps, but remain inline in browser snapshots/exports.
- **Backup availability is not guaranteed.** `createBackup` catches a storage failure and returns no success flag; callers proceed. There is one local backup slot. This was code-reviewed, not fault-injected in the audit.
- **Performance is a growth risk, not a demonstrated typical-use crisis.** Files: app.js 807,220 B / 16,274 lines; style.css 199,998 B / 7,710 lines; index.html 93,467 B. A single-run, unthrottled desktop synthetic recipe-render probe measured 15.1 ms at 40 recipes, 85.9 ms at 300, 213.9 ms at 1000; the whole document had about 97,263 nodes at 1000. Local saves measured 0.7/1.3/3.3 ms without photos. These are microbenchmarks, not phone latency, cold-start, network payload, p95, or Core Web Vitals measurements.

## Existing AI and conversational capabilities

- Home recommendations, effort/equipment ranking, use-soon suggestions and flavor matching already use deterministic helpers. They do not need a new model provider.
- AI Prep Brief already exports recipe facts, scaled ingredients, equipment and shared preparation, explicitly preserving not stated. Copy/paste into external chat is the current sequence-planning boundary; the app does not itself generate a timed cooking schedule.
- Current bridge source and connected Meal Prep MCP v2 tool metadata both expose nine tools: `get_inventory`, `get_ready_food`, `record_ready_food`, `consume_ready_food`, `mark_out_of_stock`, `mark_in_stock`, `set_inventory_quantity`, `consume_stock`, `add_stock`. No production tool was called for this audit.
- The bridge already has stable ids, revision preconditions, distinct auth scopes, narrow domain operations, bounded inputs and local regression coverage. It writes the same canonical fields rather than maintaining a competing inventory. Recording ready food deliberately does not deduct raw ingredients or complete a plan.
- Browser deduction uses guessed gram equivalents; bridge consumption uses conservative unit rules. Resolve this behavior gap before extending conversational cooking actions.
- Read responses omit pantry expiry dates and cooked-meal shelf-life fields. Ready-food reads provide cookedDate/storage but not enough to compute user-specific expiry; non-staple `inStock` is true based on record existence, even for zero quantity. Conversation cannot reliably supply the missing truth from these outputs. Any later enhancement should extend these existing reads additively with derived freshness/availability, using the same corrected rules.

## Design opportunities and measurement discipline

- Reduce navigation only after correctness: make the current next-action link carry users through the four stages; avoid a second wizard. Existing baseline is 11 clicks for one batch/one ingredient through consuming a portion. A later UX experiment can target ≤9 without removing needed recovery/confirmation. Do not claim time saved from click counts alone.
- Reuse planned weeks and existing favorites before building new recommendation surfaces. Keep the optional calendar; clarify why scheduling consumption and planning a cooking batch differ so the same recipe is not unintentionally shopped twice.
- Show known shopping shortfalls, unavailable quantities and unpriced lines before adding retailer APIs or another price engine. Price-book and nutrition figures remain estimates dependent on data quality; this audit did not verify current market prices or nutrition accuracy.
- Prefer current prepared flavors/ready portions when suggesting a quick meal, once freshness is dependable; avoid recommending another cooking task when usable food already exists.
- Hold performance work to an observed threshold: measure p50/p95 tab/filter/render times at realistic recipe/pantry sizes on a specified phone or CPU profile before changing rendering. Limit work to expensive repeated scans, unnecessary hidden renders or unbounded recipe cards if those measurements justify it. A framework migration is not supported by this evidence.
- Keep a small household scorecard for two weeks: weekly planning minutes, repeat-plan actions, shopping-list corrections, unexpected missing ingredients at prep, discarded portions/items, and incorrect stock corrections. These household baselines are **not yet measured**. Acceptance should improve them against actual observed use, not substitute features-shipped counts from METRICS.md.

Stop after the three corrective outcomes and their regressions pass. Evaluate household corrections and trust before opening another feature cycle.
